# LLM-Based Testing Engine (MDTE)

An automated, general-purpose testing engine that bridges raw Java source code and executable JUnit test suites using Large Language Models (LLMs). 

This prototype applies **Model-Driven Test Design (MDTD)** principles—specifically Input Space Partitioning (ISP) and Base Choice Coverage (BCC)—to autonomously analyze code, generate test requirements, and execute compilable test scripts.

## 🚀 Features

* **Pluggable LLM Architecture:** Seamlessly switch between Google Gemini, OpenAI, and Anthropic Claude backends.
* **Semantic Test Oracles:** Goes beyond traditional search-based testing by understanding code intent to generate meaningful assertions.
* **Generation-Validation-Repair:** Features an automated loop that catches compilation errors and feeds them back to the LLM for self-correction.
* **Zero-Touch Execution:** Automatically compiles the generated Java test class and runs it against the `JUnitCore` runner, providing terminal-native pass/fail metrics.

## 🛠️ Prerequisites

To run this engine locally, ensure your environment meets the following requirements:

1. **Python 3.9+**
2. **Java Development Kit (JDK)** (`javac` and `java` must be accessible via your system PATH).
3. **JUnit Dependencies:** Download `junit-4.13.2.jar` and `hamcrest-core-1.3.jar` and place them inside the `lib/` directory.

### Python SDKs

Install the corresponding SDK for your chosen LLM backend:

```bash
# For Gemini
pip install google-genai

# For OpenAI
pip install openai

```

## 🔑 Authentication Setup

You must expose your API keys as environment variables.

**For macOS/Linux:**

```bash
export GEMINI_API_KEY="your_gemini_api_key"
export OPENAI_API_KEY="your_openai_api_key"

```

**For Windows (Command Prompt):**

```cmd
set GEMINI_API_KEY="your_gemini_api_key"
set OPENAI_API_KEY="your_openai_api_key"

```

*(Note: The Claude backend requires the Anthropic `claude` CLI tool to be installed and locally authenticated).*

## 💻 Execution Instructions

Run the engine via the command-line interface. Provide the path to the target Java file and specify your desired backend (`gemini`, `openai`, or `claude`).

**Basic Execution:**

```bash
python3 llm_test_engine.py targets/Grade.java --backend gemini

```

**Adjusting the Repair Budget:**
If the LLM generates syntax errors, the engine will feed the compiler trace back to the LLM to fix it. You can adjust how many repair attempts it is allowed to make (default is 1):

```bash
python3 llm_test_engine.py targets/ArrayMin.java --backend openai --repair 3

```

## 📊 What to Expect (Output)

Upon execution, the engine operates silently in the background and will print a final transcript containing three artifacts:

1. **ISP & BCC Rationale:** The mathematical breakdown of the input space blocks and test coverage requirements.
2. **Compilation Output:** The results of the `javac` compiler against the generated test class.
3. **JUnit Execution Results:** The standard JUnit runner output (e.g., `OK (7 tests)` or assertion failure traces).

The generated `<Class>Test.java` file will be permanently saved in the `out/` directory for manual inspection.

## ⚠️ Limitations & Academic Note

This project is a prototype designed to demonstrate the feasibility of LLM-augmented Software Quality Assurance.

* **Probabilistic Nature:** LLMs are non-deterministic; they cannot provide the absolute mathematical coverage guarantees of traditional graph-based algorithms.
* **Hallucinations:** The engine may occasionally invent ghost variables or fabricate API dependencies. The Generation-Validation-Repair loop is designed to mitigate, but not entirely eliminate, these occurrences.
